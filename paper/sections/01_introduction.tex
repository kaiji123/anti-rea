\section{Introduction}\label{sec:intro}

Code that runs on hardware the attacker controls can eventually be read, so the strongest
protection for an algorithm is not to ship it. Software protection has long accepted that
every client-side defence is a cost multiplier, not a barrier
\cite{collberg1997taxonomy,collberg2002watermarking,schrittwieser2016obfuscation}. Studies of
professional attackers show that they defeat layered obfuscation by combining static and
dynamic analysis and by focusing on the small region that holds the asset
\cite{ceccato2017hackers}.

Two shifts make that cost multiplier smaller. First, analysis tools are scriptable end to
end: Ghidra exposes a headless analyser and scripting API \cite{nsa2019ghidra}, frameworks
such as angr automate symbolic and dynamic analysis \cite{shoshitaishvili2016sok}, and Frida
injects JavaScript hooks into running processes to trace, patch and dump memory
\cite{frida}. Second, learned models now lift binaries toward readable source and recover
names and types: DIRE and DIRTY predict identifier names and types from decompiler output
\cite{lacomis2019dire,chen2022dirty}, and LLM4Decompile trains language models to decompile
x86 binaries end to end \cite{tan2024llm4decompile}. An automated reverse-engineering agent
(the original blueprint for this design calls such a toolkit an \enquote{REA}) can therefore chain
dumping, decompilation and semantic recovery with little human effort. The scarce resource
for the attacker is no longer analyst time; it is access to the code.

Removing that access is an established defence. Client/server code splitting moves selected
code to a trusted server so that the shipped client is incomplete; it goes back at least to
DISSECT \cite{valdez2001dissect}, was applied to program slices \cite{zhang2003hiding},
combined with remote attestation \cite{viticchie2016reactive}, and has been measured against
human attackers \cite{viticchie_ese_splitting}. Offloading work from a constrained client is
likewise well studied, with performance rather than secrecy as the goal
\cite{cuervo2010maui,chun2011clonecloud,kang2017neurosurgeon}.

This paper revisits client/server code splitting for AI-assisted reverse engineering. We
keep an application's high-value logic on servers the vendor controls and leave the client
a thin shell that handles input, local rendering and commodity features and reaches that
logic through attested calls. We call this design Server-Assisted Hybrid Execution and
AI-Optimized Cloud Shielding (SA-HEACS). The split and its attested call path follow prior
work (\cref{sec:related}); what we add is the machinery to run the split economically and
to change it as a product ages.

This paper makes two contributions:
\begin{enumerate}
  \item A learned orchestrator that decides execution locality under a hard security
        constraint and uses micro-batching and Markov prefetch to offset the cost and
        latency of remote execution, with pseudocode and runnable Python
        (\cref{sec:orch}).
  \item A Dynamic Feature Promotion/Demotion Pipeline that scores each feature's IP value
        and clone risk and moves it between cloud-only, hybrid and client-local tiers over
        the product's lifecycle (\cref{sec:lifecycle}).
\end{enumerate}
To support them, we describe the split architecture and its attested request protocol,
which follow established code-splitting and attestation designs (\cref{sec:arch}); give a
threat model for AI-assisted reverse-engineering pipelines that states which attacks the
split removes and which it does not (\cref{sec:threat,sec:security}); and provide an
evaluation methodology and a reproducible simulation of cost and latency trade-offs, with
the limits of what simulation can show (\cref{sec:eval}).
All code is listed in \cref{app:code} and runs as shipped; every program output quoted in
the text is read from the output of that code.
